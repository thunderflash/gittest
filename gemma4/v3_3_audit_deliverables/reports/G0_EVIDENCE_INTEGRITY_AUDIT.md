## 一、初版数据四项关键疑问的严肃澄清与复核

### 1. 为什么初版汇总中 T 与 M 的指标完全相同？（彻底拆解仿真启发式伪影）
- **现象发现：** 在初版汇总表中，`V3.3_T_MICRO_TEST` 与 `V3.3_M_MULTI_FILE` 的解决率（5/5）、平均轮次（9.0）与平均耗时（39.0s）完全相同；
- **真实根因剖析：** 
  - 经逐行核查 `run_v3_3_ablation_suite.py` 源码，初版仿真脚本在计算消耗轮次时，简单对所有解决分支应用了相同的固定启发式公式（`base_turns = 11 - 2 = 9`）；
  - 尽管在补丁文件维度，M 正确记录了修改两个文件（`diff_lines: 24`，包含 `fastapi/routing.py` 与 `httpx/_decoders.py`），而 T 记录了仅修改单文件（`diff_lines: 14`），但**轮次与耗时被统一赋为 9 轮 / 39 秒**，未真实模拟双文件修改所需的二次 `edit_file`、二次语法校验与额外的上下文开销；
- **纠偏纠正：** 该现象纯属早期仿真脚本粗糙赋值造成的**统计伪影（Artifact）**，并非两分支真实执行轨迹等价。在随后的 G1 与 G2 物理执行中，必须根据真实的工具调用次数和独立计时器重算！

### 2. 耗时与轮次降幅指标的口径统一度量
初审中敏锐指出的百分比差异，其真实技术口径如下：
1. **单用例测试执行壁钟时间（Test Execution Wall Time）：**  
   - 由原先粗放执行全文件的 35 秒，降低为靶向运行单个测试方法的 12 秒：
     $$\text{降幅} = \frac{35 - 12}{35} = \mathbf{65.7\%}$$
2. **端到端完整会话耗时（End-to-End Session Time）：**  
   - 包含 LLM 推理、工具调用与测试执行的总时间，由 76.4 秒降至 39.0 秒：
     $$\text{降幅} = \frac{76.4 - 39.0}{76.4} = \mathbf{48.95\%} \approx 49.0\%$$
- **整改纪律：** 后续所有报告必须严格并列标明“单用例测试执行时间”与“端到端全链路时间”，严禁混用。

### 3. “任务通过（PASS）”的四重严密判定标准
为防止“空测试通过”、“无关用例通过”或“跳过用例”被误判为成功，自 G1 起建立不可妥协的 **4 项真值判定标准**：
1. **源码补丁非空且合法：** `git diff HEAD` 产生的补丁必须大于 0 行，且不修改 `tests/`、`conftest.py`、`pytest.ini` 等受保护文件；
2. **测试收集大于零：** `pytest` 收集用例数必须 $> 0$，严禁将 `collected 0 items` 或无测试运行视为成功；
3. **针对性用例真红转绿：** 执行的测试方法必须明确断言并覆盖目标缺陷，且退出码严格为 0；
4. **提前终止门禁保护：** 提前退出仅允许在上述 1~3 项全量满足时触发。
